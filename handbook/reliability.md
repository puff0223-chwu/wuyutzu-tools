# 🛡️ 穩定、速度與資料正確

> 開發手冊的「字典」：用到才查。開工必讀的是 [`HANDBOOK.md`](../HANDBOOK.md)（小抄）。
> 2026-11-12 從第二版完整手冊拆出，內容沒有刪減。

> 老師最在意的三件事：**連線穩、速度快、資料對**。這一章是做到這三件事的固定做法，新系統一開始就照做。

### 5-A 規則只寫一次

- **遊戲／評分規則寫成純函式**（只處理資料、不碰資料庫）：老師頁、伺服器（學生動作）、模擬模式都呼叫同一支（英勇學院 `engine.js`＋`actCore`、謎案課堂 `core.js`），行為一定一樣，也好測試。
- 誰看得到什麼、能不能做，統一由一支函式決定（例：情報板 `canSee()`、捷徑 `linksOf()`），伺服器算好、前端只負責顯示。
- 判斷集中：例如成績調閱室「這一欄能不能打字、重算要不要保留、匯入要不要寫入」全部用 `isEditableCol／isStoredCol／hasFormula`，不要各處自己寫 `type === 'input'`。
- 老師版的特殊動作另寫函式，不要借用學生那條路（老師「免費重抽」不能走學生技能流程，那條會扣魔力、算次數）。

### 5-B 兩個人同時改，不會互相蓋掉

- **版本號（樂觀鎖）**：每筆資料有 `rev`，更新時 `where rev = 我看到的版本`；對不上就重讀、重算、再試（英勇學院每個角色、謎案課堂日誌與作品、任務狀態 `casPatch`）。
- **版本號不要用 `updated_at`**：老師給回饋也會改到它，學生存檔就莫名衝突 → 另外用只有「內容改了」才 +1 的 `rev`。
- 一次動作的所有寫入（數值＋流水帳＋待結算）用一支資料庫函式**一次寫完**（`vc_commit`），不會寫一半。
- 衝突時給學生清楚的選擇（改用組員的版本／用我的版本蓋過去），並能先看組員版本。
- Firebase 多路徑 update：規則看的是「寫入前」的資料 → 有依賴關係的先寫（先寫 meta）。
- 單一裁判／主持機：先 `await` 寫入自己的 id 再開始監聽，不然重新整理會誤以為被接手。
- **跟著身分的東西要每次同步**：隊長被換隊就不算隊長（判斷時確認「這個學號還在這一隊」）；隊長技能在每個動作開始前同步一次——不是隊長就清掉、送審中的退回並退還花費。比在每個換身分的地方各自清理可靠。

### 5-C 網路不穩也不會出錯

- **自動重送的前提是「重送不會出錯」**（冪等）：
  - 用 upsert（唯一鍵）而不是 insert；
  - 發文帶學生端產生的編號（`cid`），同一個編號只存一次；
  - 按讚帶「想要的結果」（`want`），重送不會變回去；
  - 刪除找不到就當成功；
  - 伺服器發現「最後編輯是自己、內容一樣」就直接回成功（第一次其實存成功、只是回應掉了）。
- **不要重送的**：新增（insert）、樂觀鎖的條件更新（重送會變成「被搶先」）、改密碼（重送會變成「舊密碼不對」）、寫入類 POST（避免同一個技能用兩次）。
- **每一層都要有逾時**（AbortController）：學生讀 12 秒／送出 25 秒、老師 20 秒、伺服器連資料庫 8 秒 → 回 503（學生端自動重試），不要等到 Vercel 函式逾時。
- 老師頁的修改、刪除、upsert 遇到斷線自動再試 2 次；GET 由 supabase-js 自己重試。
- **自動存檔失敗一定要把「待存」放回去**，3、6、12… 秒重試，狀態顯示「⚠️ 存檔失敗，自動重試中」（曾經失敗後被當成已存）。
- **即時通知只是「加速」**：Realtime 斷線、被防火牆擋都可能 → 一定要有定時補抓（例 20 秒），並顯示連線燈號。即時通知只廣播「有變動」，學生收到後自己呼叫 API 重抓（不會被偽造的廣播騙到資料）；很多人同時發文時隨機延遲 0.6～1.8 秒再抓、合併成一次。
- **斷線不掉資料**：先存本機佇列（localStorage／IndexedDB），送成功才移除；學生草稿存在手機（重新整理不見不了）。
- **存檔要讀回確認**：寫入 → 再讀一次核對版本號，畫面永遠顯示資料庫的真內容；離線時擋住存檔（Firebase `.info/connected`）；Firebase SDK 離線寫入會排隊、promise 一直不回 → 加逾時說明。
- 帳本更新「**先寫新的、再刪舊的**」：中途斷線也不會有空窗。

### 5-D 資料量變大也不會壞

- **Supabase 一次最多回傳 1000 列**，超過不報錯、悄悄少資料 → 可能變多的清單一律一頁一頁拿到完（`qAll`／`mustAll`），用唯一欄位排序換頁才不漏。
- **清單從一開始就把篩選與分頁做在資料庫端**，不要整批抓回前端再篩（資料少時測不出來）；Excel 匯出另外用同一組條件重查全部。
- **流量大戶通常是「每次都帶的大欄位」**：圖片（data URL）不跟著清單一起讀，另外用「圖片版本號」抓、前後端都記住（謎案課堂情報板讀取量少 99%）。
- 全班同時重新整理同一個頁面：伺服器同一時間的請求共用一次讀取（2 秒內），新鮮度靠「變動時間」保證；寫入與權限判斷一律不共用。
- Firebase：純數字的 key 會變陣列 → 用 `a1`、`a2`；浮動數值先算「簽章」，有變才寫；會持續變多的公開節點超過 500 筆改成只抓本學期；照片和小資料分開放。

### 5-E 速度

- **覺得慢先量再改**（成績調閱室 `/speed` 測速頁）：台灣學校網路到首爾 66ms、新加坡 74ms、東京 39ms，差異不大；真正卡的是「第一次連線」0.7～0.9 秒和伺服器冷啟動。
- Vercel API 和 Supabase 放**同一區**（`vercel.json` 的 `regions`，先查 Supabase 的 Project region）。
- 登入頁一打開就暖機（呼叫不查資料庫的 ping API、先打 Supabase health）、`<link rel="preconnect">`。
- 多支 API 合併成 `[action].js`（減少冷啟動）；互不相依的查詢用 `Promise.all`；能一次帶回的資料不要讓前端再跑一趟；可預測的資料提早拿（prefetch）。
- **定時更新先比「指紋」（英勇學院，2026-11-13）**：資料庫函式把「這個人看得到的資料」做成 md5（`vc_sig`），每幾秒只問指紋，一樣就回 `{ same }`，不一樣才整包讀。指紋**一定要在讀資料之前拿**（中間有人改，下一輪指紋不同會再讀，不會漏）；自己剛寫完的回應不給指紋（下一輪一定整包）；每幾分鐘強制整包一次（跨過每日恢復時間）；有到期時間的待結算一起回最早截止時間，過了就整包。還沒跑 SQL → 指紋是 null，照舊每次整包（新程式可以先上線）。
- **寫完直接套用、不要整包重讀**：寫入函式回傳新版本號，前端把剛寫的值套到手上的狀態（`applyCommit`）；老師頁按按鈕直接用手上的狀態算，版本不對才重讀 → 一次按鈕從 3 輪連線變 1 輪。
- **全班同時打開會一起搶著做「每日恢復」**：打開頁面順手做的寫入只試 1 次，撞到就代表別人做了 → 直接讀現況給他看，不報錯。
- **閒置降頻**：3 分鐘沒碰手機 → 定時更新從 15 秒變 45 秒；畫面在背景就停。
- 大型程式庫用到才載入（xlsx 約 430 KB、Supabase 即時連線約 60 KB）：學生頁先出畫面。

### 5-F 資料正確

- **比較「有沒有改過」不要用 JSON 字串直接比**：Supabase jsonb 會把 key 重新排序 → 一直顯示「有還沒儲存的變更」。用不管順序的比對（`sameData`）；模擬資料庫也要照 jsonb 排序，測試才抓得到。
- 學生查成績只讀「已經算好的結果」（同步時就把帶入值與公式結果一起寫好），速度不變也不會算錯。
- 把別人的資料（試算表公式、題庫）搬進系統，**一定要驗算**（見 6-K）。
- 公式、換算有錯時退回安全的預設（百分制），不讓成績壞掉。
- 還沒跑新 SQL 時：讀新欄位失敗就退回舊做法，不讓整頁壞掉（升級 SQL 一定先跑、程式後上線）。

### 5-G 時間

- 時間用**伺服器時間**：Firebase 規則 `=== now`；Supabase 系統開頁時向伺服器問時間（取來回最快的一次，誤差約 ±0.1 秒），不要相信學生手機或投影電腦的時鐘。
- 截止時間一律當**台灣時間**算（加 `+08:00`）；日期用本地時間組字串，**不要用 `toISOString`**（台灣週一 00:00 會變成 UTC 週日）。
- 「到期」「每日恢復」不需要排程：誰打開頁面時順手處理到期的、補上經過幾個恢復時間點。

### 5-H 一個頁面要「跟著另一個頁面」時（教師展覽館 ↔ 事務所首頁，2026-11-08）

- **新增容易、修改難察覺** → 每筆對應資料存一份「上次確認過的快照」（展覽館卡片的 `mref` 存首頁工具的名稱、一句話、功能清單…），下次逐欄比對，改了哪一欄、清單加了／少了哪幾項都列給老師看；老師按「✔ 不用改」＝把現在的樣子記成新快照。
- **自動跟 vs. 提醒**：身分類欄位（名稱、圖示、**位置**：分類、小分類、順序）可以讓老師選「自動跟」；內容類（說明、一句話）只提醒不自動改（常常是刻意寫得不一樣）。
- 同步中的項目直接照來源排，不讓這邊上下移（顯示 🔗＋「要搬家請改首頁」），不然兩邊會打架。
- **舊資料升級要「不會突然變」**：沒寫的欄位一律當「關」，第一次由管理頁幫忙判斷（名稱一樣的才打開同步）。
- **一個入口包好幾個系統** → 做成「套組」：套組一個開關＋每個成員自己的開關與狀態；成員各有說明頁、返回鍵回套組；申請可以單獨、也可以一次帶好幾個；成員和套組同分類時自動不重複出現。
- 來源頁的「籌備中」項目（沒有網址）在跟隨端一律略過，不要當成新工具提醒。
